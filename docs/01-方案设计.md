# 01 · 方案设计

> 本文件回答四个问题：**给谁用、解决什么、怎么实现、怎么证明有效**。
> 这份文档同时也是 500 字工作介绍的素材来源。

---

## 1. 一句话定位

**把后勤报修工单从「自由文本」变成「结构化派单指令」**，让调度员从"读完再判断"变成"看一眼就确认"。

---

## 2. 目标用户与场景

### 人物画像

| | |
|---|---|
| **姓名** | 李老师（化名） |
| **角色** | 某高校后勤保障处 · 维修调度岗 |
| **日常** | 同时盯着 3 个入口（电话记录、企业微信报修群、线上报修表单），每天处理 80–150 条工单 |
| **工具** | Excel + 微信群 + 电话 |
| **痛点** | 每条工单要人读一遍，判断"这该派给水电班还是木工班""这个急不急"，再打电话通知班组 |
| **时间压力** | 上午 8:00–10:00 是报修高峰，经常积压；夜里只有值班员，紧急工单容易漏 |

### 一条工单的完整生命周期（现状）

```
学生提交「3 号楼 502 卫生间水管接口漏水，地上已经积了一层」
        ↓
调度员人工阅读 → 判断类别（水电）→ 判断紧急度（紧急，有积水/可能漏到楼下）
        ↓
微信/电话通知水电班 → 班组排期 → 上门 → 回填结果
```

**问题出在第二个箭头**：判断完全依赖个人经验，新人上手慢；高峰期积压；夜间漏判。

### 核心场景（产品要覆盖的）

| 场景 | 输入 | 期望输出 |
|---|---|---|
| 高峰期批量分派 | 一条工单原文 | 类别 + 紧急度 + 建议班组 + 置信度 |
| 夜间值班兜底 | 同上 | 紧急度判为"紧急"时高亮提醒，必须人工确认 |
| 新人培训 | 历史工单 | 给出判断依据（关键词、相似历史工单） |

## 3. 产品价值

| | 现在 | 用了之后 |
|---|---|---|
| 单条工单判断耗时 | 20–40 秒 | 2–3 秒（看一眼确认） |
| 紧急工单漏判 | 依赖值班员状态 | 模型高召回 + 低置信度强制人工复核 |
| 新人上手 | 跟师傅 2 周 | 有建议 + 依据，3 天能独立 |
| 数据沉淀 | 无 | 每条工单都有结构化标签，可做统计和排班 |

**可量化的验收指标**：
- 类别 Top-1 准确率 ≥ 85%，macro-F1 ≥ 0.80
- **紧急工单（P0）召回率 ≥ 0.95**（漏判代价最高，宁可多报）
- 端到端响应 P95 < 300ms（BERT-base，CPU）

---

## 4. 功能范围

### 做（MVP）

- 单条工单文本 → 类别 / 紧急度 / 置信度 / 建议处理组 / 相似历史工单 Top-3
- 批量粘贴（每行一条）→ 表格结果 → 导出 CSV
- 低置信度（< 阈值）自动标注"建议人工复核"
- 使用说明、加载状态、错误提示

### 不做（明确划界，避免范围失控）

- 不做用户登录/权限（评审用演示模式）
- 不做工单流转、派单闭环（那是 OA 系统的事）
- 不做图片识别（"拍张照报修"是下一步）
- 不做多语言

## 5. 技术方案

### 5.1 任务定义

**多任务文本分类**（一个编码器，两个分类头）：

```
输入: text (+ 可选 location)
        ↓
  BERT/RoBERTa 编码器
        ↓
   [CLS] 向量 (768)
    ├── 类别头 → 6 类（softmax）
    └── 紧急度头 → 3 类（softmax）
```

**为什么要多任务**：两个任务共享语义特征（"漏水"既提示类别也提示紧急度），多任务能省一半训练成本，
且实测通常比两个独立模型略好。同时输出两个结果也让网站信息更丰富。

### 5.2 数据

| 项 | 方案 |
|---|---|
| 来源 | **自建**：从报修平台导出（脱敏）、校园论坛/贴吧公开帖子、模拟用户口吻撰写 |
| 规模 | 目标 1500–2000 条（训练 70% / 验证 15% / 测试 15%） |
| 标注 | 单人标注 + 抽取 10% 双人复核，算 Cohen's Kappa（目标 > 0.75） |
| 类别 | 6 类，见 [02-数据标注规范.md](02-数据标注规范.md) |
| 增强 | 同义改写、口语化改写（用于扩充稀有类别） |

> ⚠️ 数据是这个项目最大的风险点。如果只能拿到 500 条，优先保证**每类至少 60 条**，
> 并接受 macro-F1 下降。样本不足时**必须**在报告里如实说明。

### 5.3 模型选型

| 方案 | 模型 | 用途 | 预期 |
|---|---|---|---|
| **Baseline** | TF-IDF(char 1-3 gram) + LinearSVC | 证明"深度学习确实有用" | macro-F1 ~0.70 |
| **主模型** | `hfl/chinese-roberta-wwm-ext`（110M）多任务 | 最终上线 | macro-F1 0.85+ |
| 对比实验 | `Qwen3-0.6B` + LoRA | 展示大模型微调路线 | 数据少时未必更好 |

**为什么不用更大的模型**：8GB 显存 + CPU 推理部署，110M 的 BERT 是最优性价比。
如果做 LoRA 对比实验，0.6B 在 8GB 上也能跑，但推理慢 5–10 倍，不适合上线。

### 5.4 评测方案

```python
# 三个层次，缺一不可
1. 类别: accuracy, macro-F1, 每类 P/R/F1, 混淆矩阵
2. 紧急度: 三档各自的 recall，重点看 P0 的 recall
3. 端到端: 阈值扫描 → 准确率 vs 人工复核率曲线（选阈值用）
```

**阈值怎么定**：模型输出 max(softmax) 作为置信度，低于阈值转人工。
在验证集上扫描 0.5–0.95，选"人工复核率 ≤ 20% 时准确率最高"的点。

### 5.5 失败案例分析（题目硬性要求）

计划分析这 5 类失败，每类至少 2 个真实样例：

| 失败类型 | 例子 | 分析角度 |
|---|---|---|
| 上下文缺失 | 「不亮了」 | 信息不足 → 该进人工复核，模型应该低置信度 |
| 一词多义 | 「没水」=停水/水龙头坏/水管堵 | 歧义 → 看混淆矩阵里和哪类互混 |
| 跨类别复合 | 「水管漏水把插座泡了」 | 多标签问题 → 是否该改成多标签分类 |
| 领域新词 | 「充电桩」「共享洗衣机」 | 词表/OOV → 看 subword 切分 |
| 标注歧义 | 「灯一直闪」算水电还是电器 | 标注规范是否要补边界规则 |

**分析要落到"下一步怎么改"**，不能只描述现象。

## 6. 系统架构

```
┌─────────────┐   HTTPS    ┌──────────────────┐
│  浏览器      │ ─────────→ │  Nginx (443)     │
│  (静态页面)  │ ←───────── │  反向代理         │
└─────────────┘            └────────┬─────────┘
                                    │ /api/*
                           ┌────────▼─────────┐
                           │ FastAPI (8000)   │
                           │  · 模型常驻内存   │
                           │  · 置信度/阈值    │
                           │  · 相似工单检索   │
                           └────────┬─────────┘
                                    │
                    ┌───────────────┴───────────────┐
              ┌─────▼─────┐                   ┌─────▼─────┐
              │ BERT 权重  │                   │ 向量索引   │
              │ (~400MB)  │                   │ (FAISS)   │
              └───────────┘                   └───────────┘
```

**关键设计**：
- 模型**进程启动时加载一次**，不能每个请求加载（否则 3 秒起步）
- 相似工单用句向量 + FAISS，给调度员"以前类似问题怎么处理的"参考
- 前端纯静态（原生 JS），不引入构建工具，降低部署复杂度

## 7. 部署方案

两条路，按你的条件选：

| 方案 | 成本 | 备案 | 国内访问 | 适合 |
|---|---|---|---|---|
| **A. 阿里云/腾讯云轻量服务器 + 自己的域名** | 学生机 ~10 元/月 + 域名 ~30 元/年 | **需要 ICP 备案**（1–3 周） | 快 | 有域名、能等 |
| **B. 平台子域名**（Hugging Face Spaces / Railway / Render） | 免费额度 | 不需要 | 不稳定/可能被墙 | 快速上线、先跑通 |

**推荐**：先走 B 把流程跑通（一天内能看到线上链接），再迁到 A 做长期演示。
题目明确说"自有域名或稳定的平台子域名均可"，B 是被允许的。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 拿不到真实工单数据 | 项目变成"玩具" | 用公开政务热线数据替代；或明确声明是模拟数据并降低结论强度 |
| 标注量不够 | 模型效果差 | 减少类别数（6→4）；用弱监督/数据增强 |
| 服务器/域名搞不定 | 无法在线演示 | 用平台子域名兜底，提前一周试 |
| 8GB 显存不够 | 训练失败 | BERT-base 只需 2–3GB，实际够用；必要时减小 batch + 梯度累积 |
